# 周期与超时

更新日期：2026-10-14。本轮四阶段实现、规范项目定向验收和 Server／Bridge 刷新已完成。本页记录配置契约与实施清单；编译身份、测试、加载来源和现场观察见[验证记录](TimingAndTimeouts-Validation-20261014.md)。

## 设置入口与保存方式

打开 **UPilot → 高级设置 → 常规 → 周期与超时**。这里集中配置心跳、Health、命令 Watchdog、Domain Reload 复核、窗口观察、包请求与恢复、Profiler 采集默认时长、重连和监控窗口刷新。**服务重启总期限**继续放在同页的 **AI 服务维护** 区域，沿用原有项目配置与授权。

周期与超时偏好保存在本机当前项目的 `EditorPrefs` 中，不影响其他项目。服务维护参数仍保存在该项目现有配置中。“恢复周期与超时默认值”恢复本区域的默认值并保存心跳和 Health 默认值；它不修改 AI 服务维护授权、自动升级选项或该区域的重启期限。

参数有两种生效方式：

- **周期设置**：调整下一次调度，不中断已开始的 HTTP、连接或业务请求，不重发原请求。
- **有限观察设置**：在该次观察开始时复制参数和截止时间。观察途中修改默认值只影响下一次；再次 Domain Reload、继续等待或重复查询不会延长期限。界面显示的本次参数可能与新默认值不同。

界面把数值限制在下表范围内，并处理相关参数的约束。所有时间均需注意单位；`ms` 表示毫秒。

## 配置一览

| 设置 | 默认值 | 范围 | 生效与约束 |
| --- | --- | --- | --- |
| Bridge 心跳间隔 | 3 秒 | 1～600 秒 | 当前连接的后续心跳使用新间隔；通过既有变更信号唤醒等待。Server 接受间隔后，网络心跳超时为间隔的 3 倍。 |
| HTTP Health 间隔 | 10 秒 | 1～600 秒 | 调整下一次服务健康检查；一轮完成后计算下一周期，同一项目只有一份周期观察。 |
| 命令 Watchdog 检查间隔 | 2 秒 | 1～60 秒 | 仅存在活动命令时检查；下一次检查以最后实际检查时间加新间隔为准，空闲时不更新时间戳。检查频率不改变命令警告阈值或任务期限。 |
| Reload 复核间隔 | 2 秒 | 1～60 秒 | 一轮完成后到下一轮的间隔；首轮在允许复核时立即开始。 |
| Reload 单轮复核超时 | 5 秒 | 1～60 秒 | 本轮 HTTP、进程身份和只读往返共用该轮剩余预算，且不超过总期限剩余时间。 |
| Reload 复核总期限 | 120 秒 | 5～600 秒 | 必须大于或等于单轮超时；提高单轮超时时会相应提高过小的总期限。 |
| Reload 最大复核次数 | 30 次 | 1～100 次 | 与总期限同时生效；任一上限到达便停止观察。尚未真正开始的延后探测不消耗轮数。 |
| UPM 请求观察期限 | 600 秒 | 30～3600 秒 | 在“包请求与恢复”分组；主线程开始请求时冻结本次期限，适用于包清单资源、普通 add/remove/list/search 和 UPilot 自身更新。 |
| UPM 完成检查间隔 | 100 ms | 50～1000 ms | 首轮立即检查，此后按冻结间隔读取完成状态；取消、Reset、生命周期及到期检查优先，不受该间隔延后。 |
| 包更新恢复等待 | 600 秒 | 30～3600 秒 | 用于等待 Editor Ready 和延后包修复中的一次等待；开始时固定身份、参数和截止时间，重载后继续原等待。 |
| Profiler 默认采集时长 | 30 秒 | 1～3600 秒，整数 | start 省略 `durationSec` 或传 `null` 时采用项目配置；显式数值优先并支持小数秒。开始时固定，修改及恢复默认只影响后续采集。 |
| 窗口／模态观察 | 5000 ms | 500～30000 ms | 主线程正式开始该次观察时固定预算；存在模态窗口也不会延长截止时间。 |
| 模态检查间隔 | 100 ms | 50～1000 ms | 与窗口观察预算一起固定，且不得超过本次窗口观察时长的一半。缩短窗口预算会同步收紧此值。 |
| Bridge 重连等待 | 1 秒 | 1～60 秒 | 后续重连等待使用新值，正在进行的连接请求沿用原请求。 |
| 主窗口刷新 | 400 ms | 100～5000 ms | 仅影响打开中的主窗口；关闭时卸载窗口刷新回调。 |
| 高级设置／快速调试／更新中心刷新 | 300 ms | 100～5000 ms | 三类窗口共用刷新偏好，各自关闭时卸载回调；更新中心只在周期到达或状态通知后读取界面快照。 |
| 更新完成后检查延迟 | 10 秒 | 1～60 秒 | 更新中心为原 operationId 保留一次有限延后检查；开始固定截止，重复通知不续期。 |
| 停止服务观察期限 | 30 秒 | 1～600 秒 | 从准入起计时，含身份准备、停止派发和退出／端口观察；父操作剩余期限更短时取更小值。 |
| 停止完成检查间隔 | 100 ms | 50～1000 ms | 每次停止冻结；生命周期变更、取消和截止优先于间隔，提前确认即结束。 |
| Step 管理窗口刷新 | 1000 ms | 100～5000 ms | 仅影响打开中的管理界面，不改变 Step 执行或清理期限。 |
| 服务重启总期限 | 120 秒 | 30～600 秒 | 在 **AI 服务维护** 设置；请求接受时固定，轮询或重连不续期。调整此值不授予 AI 重启权限。 |

## 观察结果与结束边界

### 更新中心与停止服务

更新中心使用已有 `DebugWindowRefreshMs` 偏好，打开时读一次快照，配置周期到达或状态变更后更新；GUI 使用缓存的更新、下载和 Reload Guard 状态。PlayMode 等待改用状态事件。周期设置变更调整下一次读取，窗口关闭卸载其 Update 和事件订阅，后台更新仍由更新服务推进。

更新完成后为该 `operationId` 安排最多一次延后 manifest 检查，冻结 `UpdateCenterPostOperationDelaySeconds`。重复终态通知不延长、不重新创建。手动检查消费延后计划；关闭、新更新、服务 Reset 和 Reload 使旧计划及网络返回失效，恢复的窗口不会重新安排旧终态的延后检查。关闭窗口也向其在途 manifest 请求发送取消，取消不触发 legacy manifest 回退；窗口代次及生命周期验证仍拦截迟到结果。本地取消不证明远端服务器已停止处理请求。打开窗口和显式检查仍保留原按需检查行为，没有新增后台更新巡检。

普通停止服务采用 `StopServerAndObserveExitAsync`，默认最多观察 **30 秒**，不是固定等待 30 秒。身份准备在工作线程内完成并受原截止约束；主线程保留经过项目、命令、PID 创建时间及端口归属验证的目标句柄，停止只派发一次。后续仅活动观察订阅 Editor Update，按冻结间隔确认原目标进程退出，再确认 HTTP／Bridge 端口可用。只有两项均确认且未超期才报告“停止成功”；进程退出但端口不可用单独报告，超时不会自动再次 Kill 或启动服务。

重复停止共享原任务与截止。准备阶段即暂停 Health 和自动修复；结束、异常、取消、Reset 和退出统一释放回调与句柄。再次 Reload 只恢复同一项目、Editor PID、服务生命周期及 PID 创建时间的原只读退出观察，不重新派发停止、不续期。已结束的停止意图也保留，阻止 Reload 自动启动 Server／Bridge，后续显式启动或重启才清除。服务硬 Reset 改变生命周期后不恢复旧观察。

主窗口、托管服务更新和主动 UPM 更新均已等待该有限结果后再交接；主窗口不会周期重试已结束的同一更新停止。外部 `OnRegisteringPackages` 是同步通知，只能启动一次观察，不能以异步等待阻止 Unity 的外部 UPM 注册。其登记后的恢复使用原停止 ID，未确认则不交接修复；失败后需人工检查原停止结果。

高级设置显示“下次设置”及当前／最近停止的冻结期限、检查间隔、有效预算、已用／剩余时间、结果和原因。普通开始日志显示“默认最多等待30秒”、本次配置和有效预算；终态仅记录一次实际总耗时，并区分停止成功、已停止无需再停、停止未确认，以及进程退出但端口不可用。异步截止仍需要 Editor 恢复调度，无法抢占其他已阻塞的原生主线程调用。

本轮实现与定向验证记录见 [更新中心与异步停止验证](UpdateCenterAndStop-Validation-20261014.md)。

### Profiler Capture

采集仅由显式 `unity_profiler_capture_start` 启动，打开窗口或修改设置不会启动采集。该工具的 `durationSec` 可以省略或传 `null`，此时由 Bridge 在实际开始时读取项目默认值；显式传入 `30` 始终表示本次采集 30 秒，即使项目默认值已经改为 45 秒。

本次采用的时长通过 start/status/stop 结果的 `durationSec` 返回，运行中修改设置或恢复默认不改变它。现有采样回调在检测到期后停止，手动 stop 也会释放 Timer、Update 订阅和 Recorder；status 查询不启动采集或续期。

Server 与 Bridge 都应加载新代码，并刷新 MCP 客户端工具列表。新 Server 为省略时长发送内部 `useConfiguredDuration=true` 及数值兼容值 `durationSec=30`；旧 Bridge 忽略该标记并仍采用 30 秒，不能据此宣称项目默认值已生效。旧 Server 发来的显式数值请求保持原行为。

本项已完成规范项目关联编译、18 项定向 EditMode、84 项 Python 回归和六种现场调用验证，记录见 [Profiler 默认时长验证](ProfilerCaptureDuration-Validation-20261014.md)。

### Domain Reload 复核

已验证的服务经历 Domain Reload 后，复核已有进程、服务身份和只读往返，不借复核重新启动服务或恢复旧业务任务。复核记录保留观察 ID、开始时间、原截止时间、已用次数、下一轮时间以及本次固定参数。

总期限或最大次数任一耗尽时，结束观察并解除回调，保留明确原因，例如 `reload_revalidation_timeout` 或 `reload_revalidation_attempts_exhausted`。一次正在进行的复核再次遇到 Reload 时恢复同一记录，不重新计时或清零次数。复核未通过时不能仅凭历史启动成功显示为本次已验证。

高级设置显示最近复核 ID、本次参数、已用次数、剩余时间和结束／最近原因，便于区分“下一次默认值”和“本次实际预算”。

### 窗口和模态观察

同步响应从请求进入起最多等待 **5.2 秒**。如果已开始的原观察仍在继续，响应返回 `pending`，后续使用原 `commandId` 查询，不再次发起关闭、菜单或窗口操作。尚未开始的动作在响应等待边界失去执行权，避免排队超时后迟到执行。同步等待与观察预算是两个不同的时间边界。

观察截止后解除检查回调和计时器，即使用户仍未处理模态窗口。观察终态仅代表本次观察已经结束；是否实际关闭、命令是否返回仍由 `closeVerified`、`commandReturned` 等实际结果证明。超时或取消后到达的旧回调不能把原终态改写为成功，也不会自动点击用户对话框。

### 包请求与恢复

`resource.packages` 是 MCP Resource `unity://packages/list` 的按需读取入口，只有收到资源读取请求才启动一次 UPM 请求；启动、心跳、周期 Update 或打开高级设置都不会主动读取该包清单。普通工具 `unity_package_list` 是另一入口。客户端重复读取资源会形成独立请求。

资源读取、普通 add/remove/list/search 和 UPilot 自身更新共用有限异步观察，主线程启动一次请求后返回，不使用同步睡眠等待 UPM。活动观察挂载 Update，成功、失败、异常、取消、到期、Reset、Reload 和退出统一结束并解绑；Bridge Reset 也结束尚未开始的排队观察。没有活动请求时不保留观察 Update。

本次期限与检查间隔在主线程实际开始时冻结。高级设置只读取本地观察记录，展示请求身份、类型、本次参数、状态、已用／剩余时间和结束原因；没有活动请求时保留最近一条终态。上方“下次请求参数”修改及恢复默认不改变当前观察。UPilot 包注册成功可能早于轮询完成，此时先结束旧观察，再交接 Reload／恢复，迟到结果不能重新交接或修改新观察。

`UPM_OBSERVATION_TIMEOUT` 表示本地观察结束且 UPM 最终结果未知，不表示物理取消安装／卸载，也不会自动重发。期限判断仍依赖 Editor 主线程恢复调度，不能抢占已阻塞的原生调用。

以下 Server 响应等待预算保持固定，与可配置的 Unity 本地观察及成功后的恢复等待分别计算。Server 等待超时不会自动停止 Unity 侧执行。

| 请求 | Server 响应等待上限 |
| --- | --- |
| 包清单资源读取 | 30 秒 |
| add／list／search | 120 秒 |
| remove | 60 秒 |

等待 Editor Ready 和延后包修复保留各自的原操作身份与截止时间。完成、失败、取消或到期时统一解除等待；停止／重置使已排队的旧回调失效，避免其再次进入原流程。观察结束不等于包更新成功，原更新结果仍需实际证据。

本轮五项后续优化已实现，验证见 [UPM 与 Server 验证记录](UpmAndServer-Validation-20261014.md)。Server refresh 在锁内最多读取一次内容，同一字节用于哈希和解析，未变内容复用解析字典；按需权限检查仍读取文件，环境覆盖及端口重启提示保持原规则。稳定且完全匹配的已持久化终态心跳复用单条编译关联缓存，首个终态、活动编译、新批次、身份变化和持久化失败重新验证；显式批次查询仍检查数据库证据，心跳新鲜快照继续持久化。SQL 计数证据来自隔离 Python trace，未测生产 SQL 或 CPU 收益。

### 命令 Watchdog

Watchdog 复用 Bridge 已有的主线程 pump，只在存在 `BeginOperation` 尚未由 `EndOperation` 释放的活动命令上下文时检查。空闲时跳过普通与临界检查，不创建扫描结果、不更新最后实际检查时间；必要的主线程队列处理继续运行，不另设 Timer、线程或 Update 订阅。扫描仍忽略已完成条目。

`WatchdogIntervalSeconds` 按项目保存，默认 **2 秒**，范围 **1～60 秒**，支持恢复默认。Bridge 缓存有效值，并通过现有设置变更事件更新，不在每帧读取偏好。缩短间隔后若已到期，下一帧检查；延长间隔则推迟下一次检查。长时间空闲后的首个活动命令可在下一帧检查。

| 当前命令状态 | 固定警告阈值 |
| --- | --- |
| `queued` | 10 秒 |
| `executing` | 30 秒 |
| `waiting` | 120 秒 |
| `received`／其他状态 | 300 秒 |

以上时间均从命令 `ReceivedAt` 累计，状态切换不重新计时。首次超限标记 `IsStuck`、追加诊断并输出一次警告；不取消命令、不修改业务终态或任务截止时间，也不执行 SQL。检查间隔越长，警告可能比阈值延后最多一个间隔，并受主线程调度延迟影响。主线程完全阻塞时 Watchdog 也不能运行，不能据此承诺独立探测或中断阻塞。

`AutoRestartOnCriticalStuck` 沿用原行为且默认关闭：开启后，未完成命令超过 **300 秒**可能触发强制重启 Unity 编辑器。本次仅将其检查纳入活动命令门禁，保留开关、阈值与动作；该动作与只重启 Server／Bridge 的服务维护不同。

本项是四阶段之后的后续优化，已通过本次关联编译与 19 项直接相关 EditMode 验收；真实 1 秒检查间隔与空闲退出、恢复测试的自有命令释放和配置恢复均有独立证据，见[命令 Watchdog 验证记录](Watchdog-Validation-20261014.md)。不借用下方四阶段既有结果。

### 长心跳间隔与主线程诊断

网络心跳、HTTP Health 和 Editor 主线程新鲜度分别判断。把心跳设为较长间隔会延长网络断线确认时间；两次心跳之间缓存的 Editor 样本可能已经过期，Health 可响应也不能证明主线程正在推进。

`unity_hang_status` 的 `mainThreadUnresponsive`、`suspectedBusyLoop`，以及 compile／queued 诊断中的 `editorNotPumping` 支持 `true`、`false`、`null`：

| 结果 | 含义 |
| --- | --- |
| `true` | 新鲜、同一会话的样本显示主线程 pump 时间已超过原 10 秒阈值；疑似忙循环还需要 CPU 采样支持。 |
| `false` | 可用的当前证据没有达到该诊断阈值；不替代 EditorReady 或编译验收。 |
| `null` | 缺少同一会话身份、已断开、没有 pump 时间或接收样本已超过 5 秒新鲜度，不能据旧缓存判断当前卡顿或正常；疑似忙循环还会在缺少 CPU 采样时返回 `null`。 |

配套 `mainThreadObservation` 返回 `notPumping`、`reason`、`snapshotAgeMs` 和 `pumpAgeMs`。原因包括 `identity_transition_or_missing`、`unity_not_connected`、`editor_snapshot_not_fresh`、`main_thread_pump_missing`、`main_thread_pump_stale`、`fresh_same_identity_evidence`。CPU 采样完成后重新读取时间、会话与快照，避免采样等待期间把旧证据继续当作当前证据。

真实停滞可能使 Bridge 的新快照标记为非权威，因此诊断不会仅因 `authoritative=false` 就隐藏由新样本证明的停滞。此规则不放宽 EditorReady、编译身份或错误验证要求。

## 保留的固定正确性边界

- WriteBatch 注册后 **600 秒**截止、轮次首次 Refresh 前 **500 ms**收集窗口保持固定，不新增配置。共享轮次仍保留原成员、真实 owner 和关联终态证据；计时器结束不能冒充编译成功。
- EditorReady 与快照新鲜度规则不随心跳或 Health 间隔放宽。主线程诊断的 **5 秒样本新鲜度**和 **10 秒停滞阈值**继续分别判断。
- 窗口同步响应的 **5.2 秒**上限、已有任务自己的期限及维护的原接受时间不因界面刷新或重复查询重置。
- 心跳仍持久化所需的最新执行状态，compile／Reload 生命周期快照和顺序、身份、错误验证要求继续保留。先前删除的反向空心跳、窗口历史采样和重复历史裁剪不会因这些设置重新启用。
